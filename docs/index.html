Self-hosted OpenVPN appliance

Your VPN, with a second factor that can't be skipped.

davpn2fa is a self-hosted OpenVPN appliance that ships as two Docker containers: the VPN data plane and a small local admin UI. Every login is checked against a TOTP code at the PAM layer — required, no fallback, fail-closed. One compose file, no cloud, nothing to trust but your own disk.

01

Two keys to enter

A davpn2fa user carries two keys. Both are checked. Every login.

KEY 1 — DOESN'T CHANGE

The certificate

Baked into the .ovpn profile you download from the admin UI. It doesn't change — guard the file, and you guard the key.

+
KEY 2 — CHANGES EVERY 30 S

The six-digit code

From the authenticator app you scanned at signup. It rotates every 30 seconds, so a certificate copied last year is still not enough.

One key alone opens nothing.

Need a service account or a conscious bootstrap? add-user --no-totp exists — an explicit, per-user choice you make, never a silent default.

02

How a login happens

No magic layer, no dashboard in the middle — the check lives in the VPN server's own auth stack.

  1. STEP 1

    TLS handshake

    The client proves its certificate before anything else happens.

  2. STEP 2

    PAM takes over

    The session hits the PAM stack — auth is delegated there, not to a web panel.

  3. STEP 3

    pam_exec helper

    The helper asks for the 6-digit code from your authenticator.

  4. REQUIREDSTEP 4

    TOTP verify

    google-authenticator checks the code against the stored seed. Gate: required — no fallback.

  5. STEP 5

    Session opens

    Only now does the tunnel carry traffic. Not one packet earlier.

MISSING CODE · WRONG CODE · EXPIRED CODE → CONNECTION REFUSED. Same answer every time: no session. There is no "skip", no "remember this device", no override.

03

The architecture: two containers, on purpose

The part that moves packets and the part you click on are deliberately not the same container.

Capability split

The data plane gets NET_ADMIN and /dev/net/tun because it must. The admin UI gets none — it doesn't need them, so it doesn't have them.

One PKI, zero copies

Certificates live on a shared volume both containers read. One source of truth, nothing synced by hand.

Tunnels survive UI work

Rebuild or redeploy the admin UI and your tunnels stay up — the data plane doesn't care. That's why it's two containers, not one.

04

Deploy in three steps

These are the actual commands from the README. Nothing below is hand-waving.

STEP 01

Bring it up

step-1.sh
$ docker compose up -d --build

Builds and starts both containers. No installer, no wizard.

STEP 02

First boot, once

step-2.sh
$ docker exec -it openvpn init-pki $ docker compose restart openvpn

Creates the PKI — once. The restart lets the server pick it up.

STEP 03

First user

Open http://127.0.0.1:8080 and:
  1. sign in (ADMIN_EMAIL + password)
  2. create the user
  3. scan the TOTP QR with your authenticator
  4. download the .ovpn profile

The admin UI answers on 127.0.0.1 — it's not on the internet unless you put it there.

PREFER THE CLI? SAME ROOM, OTHER DOOR. docker exec -it openvpn add-user <username> [--server-ip <IP>] [--no-totp]
usernames: letters, digits, _ and -.
05

Hardening, on the record

What the appliance promises, stated so you can check it in the code.

✓ 2FA ENFORCED

The PAM gate is required — no fallback path, fail-closed. The code is part of the login, not a checkbox next to it.

✓ FAIL-CLOSED BOOT

An insecure config doesn't start with a warning — the container refuses to boot until it's fixed.

✓ LOCAL AUTH

Admin password hashed with scrypt; the API uses a bearer token compared in constant time. No external identity provider.

✓ NO CLOUD

Nothing phones home, no accounts anywhere. If it stops working, the reason is on your machine, not someone else's status page.

✓ LOCAL AUDIT

Every admin action lands in a local SQLite log — on your disk, readable with sqlite3, gone when you say so.

✓ SHIPPED CHECKED

CI runs a 29-check quality gate before publishing multi-arch images (amd64 + arm64) to GHCR.

FROM THE AUDIT LOG

davpn2fa started as a generated appliance whose 2FA was, frankly, decorative. An internal audit called it exactly that — then fixed it: the TOTP gate is now required at the PAM layer, an open redirect is gone, and the boot guard refuses insecure configs instead of shrugging at them. We kept the receipt because it's the point: the enforcement is real, and the code that proves it is yours to read.
